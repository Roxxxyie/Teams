# Балансировщик команд

Консольная программа на Go, которая делит участников из JSON-файла на команды так, чтобы суммы баллов (`points`) у команд были как можно ближе друг к другу.

## Требования

- Go 1.24 или новее

## Запуск

```bash
go run .
```

По умолчанию читается `programmers.json` из текущей папки. Другой файл можно указать флагом:

```bash
go run . -file path/to/file.json
```

Собрать исполняемый файл:

```bash
go build -o teams.exe .
./teams.exe
```

Программа задаёт два вопроса:

1. **На сколько команд делить** — целое число от 1 до количества участников.
2. **Обязательно ли равное количество участников** — `д`/`н` (также принимаются `да`, `нет`, `y`, `n`, `yes`, `no`).

## Формат входного файла

```json
{
    "items": [
        { "id": 1, "name": "Иванов Иван", "points": 75 },
        { "id": 2, "name": "Петрова Анна", "points": 25 }
    ]
}
```

| Поле     | Тип    | Описание                           |
|----------|--------|------------------------------------|
| `id`     | число  | Уникальный идентификатор участника |
| `name`   | строка | Имя (может быть пустым)            |
| `points` | число  | Баллы участника от 0 до 100 (см. [Как выставляются баллы](#как-выставляются-баллы)) |

## Как выставляются баллы

Баллы выставляют сами разработчики: каждый оценивает своих коллег. Итоговый балл участника — это сводная оценка коллег, записанная в поле `points`.

### Шкала

Балл показывает, какой вклад человек может внести в командную работу на хакатоне. Это не оценка человека в целом и не его стаж.

| Балл    | Уровень     | Что это значит |
|---------|-------------|----------------|
| **100** | Эксперт     | Может в одиночку взять ключевую часть проекта. Проектирует решение, быстро разбирается в незнакомых технологиях, помогает и разблокирует других. |
| **75**  | Сильный     | Уверенно и самостоятельно решает задачи. Помощь нужна только в самых сложных местах. |
| **50**  | Средний     | Самостоятельно решает типовые задачи, со сложными справляется с подсказками коллег. Надёжный член команды. |
| **25**  | Начинающий  | Справляется с простыми задачами. Регулярно нужна помощь и ревью. |
| **0**   | Без опыта   | Пока не может самостоятельно вносить вклад в код. Может помогать с задачами вне разработки. |

Можно ставить и промежуточные значения (например, 60 или 85), если человек между уровнями. Уровни выше — ориентиры, чтобы все понимали шкалу одинаково.

### Что учитывать при оценке

- **Технические навыки:** насколько хорошо человек пишет код и знает используемые технологии.
- **Самостоятельность:** может ли довести задачу до конца без постоянной помощи.
- **Скорость:** как быстро получает рабочий результат в условиях ограниченного времени.
- **Командная работа:** умеет ли договариваться, объяснять, помогать другим.

### Правила

1. Себя не оценивают, только коллег.
2. Оценивают только тех, с кем работали или чью работу видели. Если человека не знаешь, оценку не ставь.
3. Оценки ставятся анонимно, чтобы они были честными.
4. Итоговый балл — среднее всех оценок коллег, округлённое до целого.
5. Если оценок пять или больше, перед подсчётом отбрасываются одна самая высокая и одна самая низкая оценка. Так одна предвзятая оценка не сильно сдвигает итог.

**Пример.** Коллеги оценили участника так: 40, 50, 55, 60, 100. Отбрасываем 40 и 100, среднее из 50, 55, 60 = 55. В `programmers.json` записывается `"points": 55`.

Сбор оценок пока происходит вне программы: программа берёт уже готовые итоговые баллы из `programmers.json`.

## Пример работы

```
Загружено участников: 6

На сколько команд делить (1-6)? 3
Обязательно равное количество участников в командах? (д/н): н

Команда 1 — 1 чел., сумма баллов: 75
  #2   Липский Дима              75

Команда 2 — 2 чел., сумма баллов: 75
  #5   Суворов Дима              50
  #4   Донела Алексей            25

Команда 3 — 3 чел., сумма баллов: 75
  #1   Нестероов Данила          25
  #3   Плодущева Даша            25
  #6   Рогожкин Аркадий          25

Средняя сумма: 75.0, разброс (макс − мин): 0
```

**Разброс** — разница между суммой баллов самой сильной и самой слабой команды. Чем он меньше, тем ровнее команды.

## Как работает распределение

Это задача **разбиения чисел на k групп с близкими суммами** (multiway number partitioning). Программа решает её в два этапа (функция `Split` в `balance.go`).

### Этап 1. Жадный алгоритм «сначала самые сильные» (LPT)

1. Участники **сортируются по убыванию баллов** (`sort.SliceStable`).
2. По очереди, начиная с самого сильного, каждый участник отправляется в команду с **наименьшей текущей суммой**. При равных суммах выбирается команда, где меньше людей, а дальше — с меньшим номером.
3. В режиме «поровну» заполненные команды пропускаются. Каждая команда может получить `n / k` участников, а `n % k` команд — на одного больше.

**Почему важна сортировка по убыванию.** Крупные баллы распределяются первыми, пока команды пустые и их легко выровнять. Мелкие баллы идут в конце и «добивают» разницу. Если идти в случайном порядке, последним может оказаться сильный участник, и его уже некуда поставить без перекоса. Для режима без ограничения размеров у этого метода есть доказанная гарантия (Р. Грэхем): сумма самой сильной команды не больше чем примерно в 4/3 раза превышает лучший возможный вариант.

### Этап 2. Локальное улучшение (hill climbing)

Жадный результат часто можно улучшить. Программа перебирает все пары команд A и B и пробует:

- **Перенос:** перевести одного участника из A в B.
- **Обмен:** поменять участника из A на более слабого участника из B.

Изменение применяется, только если команды становятся ровнее. Перебор повторяется, пока находятся улучшения.

**Что значит «ровнее».** Программа минимизирует **сумму квадратов** сумм команд. Общая сумма баллов не меняется, поэтому меньшая сумма квадратов означает меньшую дисперсию: суммы команд ближе к среднему. Например, при общей сумме 150 разбиение 75/75 даёт 75² + 75² = 11 250, а 100/50 даёт 100² + 50² = 12 500.

Квадраты выбраны потому, что они наказывают за сильный перекос больше, чем за несколько мелких, и потому что значение целое и строго уменьшается при каждом изменении — поэтому алгоритм гарантированно останавливается.

**Ограничения перестановок:**

- Перенос не может оставить команду пустой.
- В режиме «поровну» перенос разрешён только из команды, где на одного человека больше, в ту, где на одного меньше (команды просто меняются размерами). Обмен размеры не меняет, поэтому разрешён всегда.

### Что важно знать

- **Результат воспроизводим.** Сортировка стабильная, при равенствах выбор однозначный, случайности нет. Один и тот же файл и те же ответы всегда дают одинаковые команды. При равных баллах участники обрабатываются в порядке файла.
- **Лучший вариант не гарантирован.** Задача NP-трудная: точное решение пришлось бы искать полным перебором, который на больших списках слишком долгий. Алгоритм находит результат, близкий к оптимальному. На текущем `programmers.json` он находит оптимум (это проверено тестами).
- **Ровно поделить иногда невозможно.** Например, при общей сумме 225 и баллах, кратных 25, две команды не могут получить поровну: лучший результат — 125/100.
- **Скорость.** Сортировка — O(n log n), каждый проход улучшения — O(n²). Для сотен участников программа работает мгновенно.
- **Порядок вывода.** Команды выводятся от самой сильной к самой слабой, участники внутри команды — по убыванию баллов.

### Правила

- В каждой команде есть хотя бы один участник.
- В режиме «равное количество» размеры команд отличаются не более чем на 1 (если участники не делятся поровну, например 7 человек на 2 команды → 4 и 3).
- Количество команд не может превышать количество участников.

## Тесты

```bash
go test ./...
```

Тесты проверяют, что каждый участник попадает ровно в одну команду, разброс минимален на эталонных примерах, размеры команд соблюдаются в режиме «поровну», а некорректный ввод приводит к ошибке.
