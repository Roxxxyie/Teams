# Балансировщик команд

Настольное приложение на Go ([Fyne](https://fyne.io)), которое делит участников из JSON-файла на команды так, чтобы суммы баллов (`points`) у команд были как можно ближе друг к другу.

## Требования

- Go 1.24 или новее
- C-компилятор: Fyne рисует окно через OpenGL и использует CGO
  - Windows: [MinGW-w64](https://www.mingw-w64.org/) (64-битный `gcc` в `PATH`), например `choco install mingw`
  - Linux: `gcc` и пакеты `libgl1-mesa-dev xorg-dev`
  - macOS: Xcode Command Line Tools
- GNU make. На Windows вместе с MinGW идёт `mingw32-make`.

## Сборка

```bash
mingw32-make          # Windows (или make, если установлен GNU make)
make                  # Linux / macOS
```

Результат появляется в папке `build/`: `Teams.exe`, рядом копия `programmers.json` и папка `examples/` с демо-файлами. Папку можно целиком скопировать на другой компьютер: Go и компилятор там не нужны.

| Цель    | Что делает |
|---------|------------|
| `build` | Собирает `build/Teams.exe` (цель по умолчанию). На Windows exe собирается без консольного окна |
| `run`   | Собирает и запускает |
| `test`  | Запускает тесты алгоритма |
| `vet`   | Статический анализ |
| `clean` | Удаляет `build/` |

Первая сборка занимает несколько минут: компилируется графическая часть Fyne. Следующие сборки идут за секунды.

Без make можно собрать и вручную:

```bash
go build -ldflags "-s -w -H=windowsgui" -o build/Teams.exe .
```

## Как пользоваться

1. **Участники.** При запуске приложение само открывает `programmers.json` из текущей папки или из папки рядом с exe. Другой файл выбирается кнопкой **«Открыть JSON…»**. Кнопка ⟳ перечитывает файл после правок. Слева показан список участников, баллы подсвечены цветом по уровню.
2. **Параметры.**
   - **Команд**: количество команд (кнопки − / + или ввод числа).
   - **Равное количество участников**: размеры команд будут отличаться не больше чем на 1.
   - **Вариант (seed)**: номер варианта распределения (см. ниже). Кнопка **«Другой вариант»** увеличивает номер и сразу пересчитывает.
3. **«Распределить»**: справа появляются карточки команд. Полоска в каждой карточке показывает сумму баллов команды: если полоски одинаковой длины, команды ровные. Над карточками выводятся средняя сумма и разброс.
4. **«Копировать»**: кладёт состав команд текстом в буфер обмена, чтобы вставить его в чат.

После изменения количества команд или галочки «поровну» результат пересчитывается автоматически.

### Варианты распределения (seed)

Обычно существует несколько одинаково ровных распределений: участников с равными баллами можно поменять местами, и суммы команд не изменятся. Поле **«Вариант (seed)»** позволяет выбрать один из таких вариантов.

- `0` (по умолчанию): участники с равными баллами берутся в порядке файла.
- Любое другое число: участники с равными баллами перемешиваются генератором с этим seed.
- **Воспроизводимость.** Тот же файл, тот же seed и те же параметры всегда дают тот же состав команд. Чтобы повторить распределение, достаточно запомнить номер. Он показан над результатом.
- **Баланс от seed не зависит.** Перемешиваются только участники с одинаковыми баллами, поэтому суммы команд и разброс у всех вариантов одинаковые. Меняется только то, кто конкретно попал в какую команду.

Это удобно, если первый вариант не подошёл (например, в одну команду попали люди, которые и так всегда работают вместе): можно нажать «Другой вариант» несколько раз и выбрать подходящий.

## Формат входного файла

```json
{
    "items": [
        { "id": 1, "name": "Иванов Иван", "points": 75 },
        { "id": 2, "name": "Петрова Анна", "points": 25 }
    ]
}
```

| Поле     | Тип    | Описание                           |
|----------|--------|------------------------------------|
| `id`     | число  | Уникальный идентификатор участника |
| `name`   | строка | Имя (может быть пустым)            |
| `points` | число  | Баллы участника от 0 до 100 (см. [Как выставляются баллы](#как-выставляются-баллы)) |

### Проверка файла перед распределением

При открытии приложение проверяет файл и выводит **все** найденные проблемы сразу, с номером участника, его `id` и именем:

| Проблема | Пример сообщения |
|----------|------------------|
| Файл не JSON или обрывается | `файл пуст или JSON обрывается (не хватает закрывающих скобок)` |
| Нет `items` или список пуст | `нет поля "items" со списком участников` |
| Опечатка в названии поля | `неизвестное поле "point" (допустимы: items, id, name, points) — возможно, опечатка` |
| Неверный тип | `поле "items.points" должно быть типа целое число, а в файле string` |
| Нет `id` или `points` | `участник №3 (id 3, «Вера»): нет поля "points"` |
| Повтор `id` | `участник №2 (id 1, «Боря»): id 1 уже занят участником №1` |
| Баллы вне шкалы | `участник №1 (id 1, «Аня»): баллы 120 вне диапазона 0–100` |

Ошибки показываются в окне «Ошибка», например:

```
Файл programmers.json: найдено проблем: 3
  - участник №1 (id 1, «Аня»): баллы 120 вне диапазона 0–100
  - участник №2 (id 1, «Боря»): id 1 уже занят участником №1
  - участник №3 (id 3, «Вера»): нет поля "points"
```

Отсутствующее поле `points` считается ошибкой, а не нулём: иначе забытая оценка незаметно превратила бы участника в «без опыта» и испортила бы баланс. Пустое имя допустимо. BOM в начале файла (его добавляют Блокнот и PowerShell) игнорируется.

## Демо-файлы

В папке `examples/` лежат готовые списки для демонстрации. Их открывают кнопкой «Открыть JSON…». Все имена вымышленные.

| Файл | Участников | Что показать |
|------|-----------|--------------|
| `small_team.json` | 8 | Баллы не кратны 25 (35, 40, 55…). На 2 командах получается 240 / 240, на 3 командах 160 / 160 / 160: ровно в обоих случаях. |
| `hackathon_30.json` | 30 | Большой хакатон: все уровни от 0 до 100. На 5 командах получается 300 / 300 / 300 / 275 / 275. Разброс 25 здесь минимально возможный: 1450 / 5 = 290, а суммы команд всегда кратны 25. Удобно показать кнопку «Другой вариант»: равных баллов много, состав меняется, а разброс нет. |
| `stars_and_juniors.json` | 10 | 2 эксперта по 100 и 8 новичков по 25, 4 команды. С галочкой «поровну» получается 125 / 125 / 75 / 75 (разброс 50). Без галочки получается 100 / 100 / 100 / 100: эксперт работает один, новички в командах по четыре. Видно, чем приходится платить за равные размеры. |
| `with_errors.json` | 5 | Файл с ошибками: баллы 120 и −10, повтор `id`, нет поля `points`. Приложение выводит все 4 проблемы сразу. |

## Как выставляются баллы

Баллы выставляют сами разработчики: каждый оценивает своих коллег. Итоговый балл участника — это сводная оценка коллег, записанная в поле `points`.

### Шкала

Балл показывает, какой вклад человек может внести в командную работу на хакатоне. Это не оценка человека в целом и не его стаж.

| Балл    | Уровень     | Что это значит |
|---------|-------------|----------------|
| **100** | Эксперт     | Может в одиночку взять ключевую часть проекта. Проектирует решение, быстро разбирается в незнакомых технологиях, помогает и разблокирует других. |
| **75**  | Сильный     | Уверенно и самостоятельно решает задачи. Помощь нужна только в самых сложных местах. |
| **50**  | Средний     | Самостоятельно решает типовые задачи, со сложными справляется с подсказками коллег. Надёжный член команды. |
| **25**  | Начинающий  | Справляется с простыми задачами. Регулярно нужна помощь и ревью. |
| **0**   | Без опыта   | Пока не может самостоятельно вносить вклад в код. Может помогать с задачами вне разработки. |

Можно ставить и промежуточные значения (например, 60 или 85), если человек между уровнями. Уровни выше — ориентиры, чтобы все понимали шкалу одинаково.

### Что учитывать при оценке

- **Технические навыки:** насколько хорошо человек пишет код и знает используемые технологии.
- **Самостоятельность:** может ли довести задачу до конца без постоянной помощи.
- **Скорость:** как быстро получает рабочий результат в условиях ограниченного времени.
- **Командная работа:** умеет ли договариваться, объяснять, помогать другим.

### Правила

1. Себя не оценивают, только коллег.
2. Оценивают только тех, с кем работали или чью работу видели. Если человека не знаешь, оценку не ставь.
3. Оценки ставятся анонимно, чтобы они были честными.
4. Итоговый балл — среднее всех оценок коллег, округлённое до целого.
5. Если оценок пять или больше, перед подсчётом отбрасываются одна самая высокая и одна самая низкая оценка. Так одна предвзятая оценка не сильно сдвигает итог.

**Пример.** Коллеги оценили участника так: 40, 50, 55, 60, 100. Отбрасываем 40 и 100, среднее из 50, 55, 60 = 55. В `programmers.json` записывается `"points": 55`.

Сбор оценок пока происходит вне программы: программа берёт уже готовые итоговые баллы из `programmers.json`.

## Пример результата

3 команды без требования равных размеров. Так выглядит текст, который кладёт в буфер кнопка «Копировать»:

```
Команда 1 — 1 чел., сумма баллов: 75
  #2 Дима — 75

Команда 2 — 2 чел., сумма баллов: 75
  #5 Дима — 50
  #4 Алексей — 25

Команда 3 — 3 чел., сумма баллов: 75
  #1 Данила — 25
  #3 Даша — 25
  #6 Аркадий — 25

Команд: 3   ·   средняя сумма 75.0   ·   идеально ровно   ·   вариант 0
```

**Разброс** — разница между суммой баллов самой сильной и самой слабой команды. Чем он меньше, тем ровнее команды.

## Как работает распределение

Это задача **разбиения чисел на k групп с близкими суммами** (multiway number partitioning). Программа решает её в два этапа (функция `Split` в `balance.go`).

### Этап 1. Жадный алгоритм «сначала самые сильные» (LPT)

1. Участники **сортируются по убыванию баллов** (`sort.SliceStable`).
2. По очереди, начиная с самого сильного, каждый участник отправляется в команду с **наименьшей текущей суммой**. При равных суммах выбирается команда, где меньше людей, а дальше — с меньшим номером.
3. В режиме «поровну» заполненные команды пропускаются. Каждая команда может получить `n / k` участников, а `n % k` команд — на одного больше.

**Почему важна сортировка по убыванию.** Крупные баллы распределяются первыми, пока команды пустые и их легко выровнять. Мелкие баллы идут в конце и «добивают» разницу. Если идти в случайном порядке, последним может оказаться сильный участник, и его уже некуда поставить без перекоса. Для режима без ограничения размеров у этого метода есть доказанная гарантия (Р. Грэхем): сумма самой сильной команды не больше чем примерно в 4/3 раза превышает лучший возможный вариант.

### Этап 2. Локальное улучшение (hill climbing)

Жадный результат часто можно улучшить. Программа перебирает все пары команд A и B и пробует:

- **Перенос:** перевести одного участника из A в B.
- **Обмен:** поменять участника из A на более слабого участника из B.

Изменение применяется, только если команды становятся ровнее. Перебор повторяется, пока находятся улучшения.

**Что значит «ровнее».** Программа минимизирует **сумму квадратов** сумм команд. Общая сумма баллов не меняется, поэтому меньшая сумма квадратов означает меньшую дисперсию: суммы команд ближе к среднему. Например, при общей сумме 150 разбиение 75/75 даёт 75² + 75² = 11 250, а 100/50 даёт 100² + 50² = 12 500.

Квадраты выбраны потому, что они наказывают за сильный перекос больше, чем за несколько мелких, и потому что значение целое и строго уменьшается при каждом изменении — поэтому алгоритм гарантированно останавливается.

**Ограничения перестановок:**

- Перенос не может оставить команду пустой.
- В режиме «поровну» перенос разрешён только из команды, где на одного человека больше, в ту, где на одного меньше (команды просто меняются размерами). Обмен размеры не меняет, поэтому разрешён всегда.

### Что важно знать

- **Результат воспроизводим.** Сортировка стабильная, при равенствах выбор однозначный. Один и тот же файл, те же параметры и тот же seed всегда дают одинаковые команды. При seed 0 участники с равными баллами обрабатываются в порядке файла, при другом seed они перемешиваются перед сортировкой (генератор PCG из `math/rand/v2` с заданным seed).
- **Лучший вариант не гарантирован.** Задача NP-трудная: точное решение пришлось бы искать полным перебором, который на больших списках слишком долгий. Алгоритм находит результат, близкий к оптимальному. На текущем `programmers.json` он находит оптимум (это проверено тестами).
- **Ровно поделить иногда невозможно.** Например, при общей сумме 225 и баллах, кратных 25, две команды не могут получить поровну: лучший результат — 125/100.
- **Скорость.** Сортировка — O(n log n), каждый проход улучшения — O(n²). Для сотен участников программа работает мгновенно.
- **Порядок вывода.** Команды выводятся от самой сильной к самой слабой, участники внутри команды — по убыванию баллов.

### Правила

- В каждой команде есть хотя бы один участник.
- В режиме «равное количество» размеры команд отличаются не более чем на 1 (если участники не делятся поровну, например 7 человек на 2 команды → 4 и 3).
- Количество команд не может превышать количество участников.

## Тесты

```bash
mingw32-make test     # или: go test ./...
```

Тесты проверяют, что каждый участник попадает ровно в одну команду, разброс минимален на эталонных примерах, размеры команд соблюдаются в режиме «поровну», а некорректный ввод приводит к ошибке. Отдельно проверяется, что каждый вид ошибки в файле даёт понятное сообщение, что один и тот же seed воспроизводит состав, разные seed дают разные составы, а разброс от seed не меняется.
